# 開票判定改善規格

> 來源：2026-08-27 選票掃描彩排（票號 20260827501／502）
> 狀態：規格已驗證，**尚未套用到正式環境**

## 背景

彩排時以 3 份掃描檔（其中票號 20260827502 掃了兩次）測試監事選票判讀，
發現的問題與既有機制盤點如下。

## 一、票號重複 — 既有機制已足夠（不需改）

| 機制 | 位置 |
| --- | --- |
| 同場次同票號唯一索引 | `supabase/tada_ballot_scans.sql` → `uq_ballot_no_live` |
| 掃描端友善錯誤 | `scan/index.html:277`（攔 `uq_ballot_no_live` → 「已掃描過，本張略過」） |
| 計票冪等 | `tada_ballot_commit`：`FOR UPDATE` 悲觀鎖 + `counted` 旗標 |

彩排中同一票號能重複掃描，是因為索引條件含 `is_test = FALSE`，
**測試票刻意排除在唯一性之外**，好讓彩排可重複執行。此為正確設計。

### 殘留缺口：票號判讀失敗時唯一性失效

`uq_ballot_no_live` 的條件是 `WHERE ballot_no IS NOT NULL`。
條碼判讀失敗時 `ballot_no = NULL`，唯一索引不生效
（`scan/index.html:255` 還會給它 `noid-<timestamp>` 的儲存路徑），
同一張票可被掃兩次並各自計票。

**對策**：`tada_ballot_commit` 增加檢查——票號為空者必須
`review_status = 'confirmed'`（人工複核補登票號）才可計入。
已寫在 `supabase/tada_vote_outcome.sql`。

## 二、0 票也會「當選」

**現況**：`election-live/index.html:140` — `if(i < seats) color = GOLD;`
只看名次不看票數。應選 3 席、候選 4 人時，0 票者會排進前 3 名而被標為當選。

彩排資料即重現此情形：許炳輝 0 票被判當選。

**對策**：得票 0 一律 `not_elected`，席次寧可從缺。

## 三、同票數以號次自動決勝

**現況**：
- 前端 `election-live/index.html:136` — `b.votes - a.votes || (a.no||0)-(b.no||0)`
- 後端 `tada_voting.sql` `vote_results` — `ORDER BY c.position, count(vt.id) DESC, c.sort`

兩處都以號次／sort 打破同票。彩排資料中許炳輝與宋元博同為 0 票，
僅因號次 3 在 4 之前就一個當選、一個候補。

人民團體選舉慣例為**同票數抽籤**，系統不應自動決定。

**對策**：同票組跨越席次／候補分界線時標記 `tiebreak`（待抽籤）。

## 根因：當選判定只存在於前端上色邏輯

「誰當選、誰候補」目前只是 `renderChart()` 的顏色，不是權威名單。
願任書、公告、會議紀錄若各自重算，勢必產生不一致。

**解法**：新增 SQL 函式 `vote_outcome(p_election)` 作為單一權威來源，
前端只負責上色。

## 實作

### 1. 資料庫：`supabase/tada_vote_outcome.sql`（已備妥）

新增 `vote_outcome(p_election UUID)`，每位候選人回傳
`votes / rank / tie_size / n_seat / n_reserve / status`，
`status` 為 `elected` / `reserve` / `tiebreak` / `not_elected`。

判定規則：

| 條件 | 判定 |
| --- | --- |
| 得票 0 | `not_elected`（席次從缺） |
| 同票組完整落在應選席次內 | `elected` |
| 同票組完整落在候補名額內 | `reserve` |
| 同票組跨越分界線 | `tiebreak`（待抽籤） |
| 名次超過 應選＋候補 | `not_elected` |

同時補齊 `tada_v_election` 缺少的
`executive_reserve` / `exec_supervisor_seats` / `exec_supervisor_reserve` 欄位
（`tada_ballot_positions.sql` 已把 `exec_supervisor` 加入 position CHECK，但席次設定沒跟上）。

### 驗證結果（PostgreSQL 16 實測，5 情境全通過）

| 情境（監事 3 席・候補 1） | 結果 |
| --- | --- |
| 彩排資料 1,1,0,0 | 兩位 1 票當選；兩位 0 票落選，**1 席從缺** |
| 5,4,3,3,1 | A B 當選；C D **待抽籤**；E 落選 |
| 5,4,3,2,2 | A B C 當選；D E **待抽籤**（爭唯一候補名額） |
| 5,4,3,2,1 | A B C 當選；D 候補；E 落選 |
| 全部 0 票 | 全部落選，席次全從缺 |

### 2. 前端：`election-live/index.html`

**（a）新增待抽籤色**

```js
const GOLD='#d4a853', GREEN='#7fae86', GREY='#4a6b52', AMBER='#e0a44a';
const STATUS_COLOR = { elected:GOLD, reserve:GREEN, tiebreak:AMBER, not_elected:GREY };
```

**（b）`tick()` 改呼叫 `vote_outcome`**

```js
// 舊
rpc('vote_results',  { p_election: election.id }),
...
renderChart(chartD, cands.filter(c=>c.position==='director'),   election.director_seats,   election.director_reserve);
renderChart(chartS, cands.filter(c=>c.position==='supervisor'), election.supervisor_seats, election.supervisor_reserve);

// 新（席次參數不再需要，判定已在 SQL）
rpc('vote_outcome',  { p_election: election.id }),
...
renderChart(chartD, cands.filter(c=>c.position==='director'));
renderChart(chartS, cands.filter(c=>c.position==='supervisor'));
```

**（c）`renderChart()` 依 `status` 上色**

```js
function renderChart(chart, arr){
  // SQL 已排序，前端僅依 rank 穩定化
  arr = arr.slice().sort((a,b)=> a.rank - b.rank || (a.no||0)-(b.no||0));
  const names = arr.map(c =>
    c.name + (c.company ? '　'+c.company : '') + (c.status==='tiebreak' ? '　⚖ 待抽籤' : ''));
  const data = arr.map(c => ({
    value: c.votes,
    itemStyle:{ color: STATUS_COLOR[c.status] || GREY, borderRadius:[0,6,6,0] }
  }));
  // 其餘 setOption 不變
}
```

**（d）圖例加一項**

```html
<div class="foot" id="foot">每 3 秒自動更新　·　🟡 當選　🟢 候補　🟠 待抽籤</div>
```

## 上線步驟

1. Supabase SQL Editor 執行 `supabase/tada_vote_outcome.sql`
2. 用彩排場次呼叫 `vote_outcome` 比對結果（`is_test` 票不受影響）
3. 套用前端 (a)～(d)，於 GitHub Pages 驗證
4. 把 `tada_ballot_commit` 的票號檢查同步補回 `supabase/tada_ballot_scans.sql`，
   避免日後重跑舊檔覆蓋
5. 正式開票前執行 `supabase/tada_election_reset.sql` 清除彩排殘留
