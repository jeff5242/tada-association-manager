# 報到機擴充：身分選單與貴賓報到

> 草案 2026-08-15｜尚未實作
> 這是 `kiosk/index.html` 的**擴充規格**，不是新建系統。

---

## 一、現況（已經有的，不要重做）

`kiosk/index.html` 已經是一台可運作的報到機：

| 項目 | 現況 |
|---|---|
| 硬體 | 觸控螢幕 1200×800 ＋ USB QR Reader（HID 鍵盤型）＋ CUPS 網路印表機 |
| 啟動 | `chromium --kiosk --kiosk-printing`，靜默出票不跳列印對話框 |
| 流程 | 掃碼／鍵盤輸入**會員編號** → `tada_v_members` 查 → 確認 → `rpc/vote_checkin` → 列印選票（含投票 token QR）→ 6 秒回待機 |
| 進度 | `rpc/vote_progress` 每 10 秒更新 `checked_in / total_members` |

名冊也都在了：

```
tada_members / tada_v_members
  member_no, name, member_type, rep, company, tax_id, is_checked_in

tada_guests（目前 32 人）
  id, name, org, tw, class, status, meal, train, note, checked_in, sort
```

**兩張名冊都已經有報到旗標。** 缺的不是資料，是取號機上的操作路徑。

## 二、要補的

1. **身分選單** —— 待機畫面讓人先選「我是會員」／「我是貴賓」
2. **雙計數** —— 左側同時顯示已報到會員數與貴賓數
3. **會員可用統編查** —— 現在只認會員編號
4. **貴賓報到路徑** —— 統編查、從名單選、或直接輸入姓名
5. **查無資料時可補登** —— 輸入姓名先完成報到，事後由秘書處處理

---

## 三、四個關鍵設計決定

### 1. 會員領票，貴賓不領票

這是**理監事改選**，只有會員有投票權。兩條路徑的產出不同：

```
會員報到  →  vote_checkin  →  印選票（含投票 token QR）
貴賓報到  →  guest_checkin →  印報到單（無投票 token）或不印
```

**不能共用同一個確認流程。** 貴賓拿到帶投票 token 的票會直接造成選務爭議。

### 2. 掃碼必須在任何畫面都能直接觸發

多了身分選單之後，**掃碼路徑不能因此變慢**。會員拿著手機會員證走過來就掃，不該強迫他先按「我是會員」。

```
任何畫面掃到會員編號  →  直接跳到會員確認畫面
```

現有的 `handleScan` 已經是全域監聽 HID 輸入，維持這個行為，只是待機畫面多了選單而已。**尖峰時段的主力路徑是掃碼，選單是給沒帶會員證的人用的。**

### 3. 統編查詢要處理一戶多人

一個公司統編可能對應**多位會員**（團體會員的代表最多 3 位，見既有的「團體代表」設計）。

查到多筆時要列出來讓他選，不能只取第一筆 —— 取錯人會讓另一位真正到場的代表報不了到。

### 4. 補登不寫進名冊

現場輸入的姓名**不自動建立會員或貴賓資料**。打錯字的姓名直接變成正式名冊是災難，而選舉場合的名冊正確性直接影響選務。

補登紀錄另存，後臺列一張清單讓秘書處事後決定：補進名冊、併到既有的人、或標記無效。

### 會員路徑

按「我是會員」→ 輸入**會員編號或統編** → 查到單筆直接進確認畫面；查到多筆列出來選。

### 貴賓路徑

按「我是貴賓」→ 三擇一：
- 輸入**統編**（`tada_guests.tw`）
- 從**名單選擇**（32 人，可捲動或依首字篩選）
- **直接輸入姓名**（查無時的補登）

## 五、後端要加的

沿用現有的 Supabase RPC 模式：

| 項目 | 說明 |
|---|---|
| `rpc/guest_checkin(p_guest_id)` | 貴賓報到，回傳姓名／單位，寫 `tada_guests.checked_in` |
| `rpc/checkin_progress(p_election)` | 一次回傳會員與貴賓的已報到數與總數，取代只算會員的 `vote_progress` |
| `rpc/checkin_manual(p_type, p_name, p_raw)` | 補登，寫入待補建檔表 |
| `tada_checkin_pending` | 補登紀錄：type、entered_name、raw_input、created_at、resolved_at |

貴賓查詢用 PostgREST 直接打 `tada_guests?tw=eq.…` 或 `?name=ilike.…` 即可，不需要另開 RPC。

會員的統編查詢**不動選舉表**，改查主名冊 `tada_members` 取得 `member_no` 後再走既有路徑，理由見第六節。

## 六、已確認的決定（2026-08-15）

| 問題 | 決定 |
|---|---|
| 貴賓報到印不印單 | **不印** |
| 身分別是否可設定 | **可設定**，媒體／工作人員／眷屬都能加，不必改程式 |
| 補登資料放哪 | **獨立一張表** `tada_checkin_pending`，不寫進名冊 |
| 統編查會員 | **改走主名冊，不動選舉表**（理由見下） |

### 統編查會員：不加欄位到 `tada_v_members`

原本提議「改 view 加 `tax_id`」，實作前重讀 `tada_voting.sql` 後**改掉這個做法**。

`tada_v_members` / `tada_v_tokens` / `tada_v_votes` 三張表之間**刻意不建立任何外鍵**，這是選舉匿名性的物理保證 —— 即使 anon key 外流、即使能讀完三張表，也無法把「誰」對應到「投給誰」。而 `tada_v_members` 本身只留 `member_no`、`name`、`member_type`、`rep`，是刻意把 PII 壓到最低的。

往這張表加統編，等於為了一個查詢便利，把更多 PII 放進選舉核心表。沒有必要：

```
輸入統編 → 查主名冊 tada_members（本來就有 tax_id / company）
        → 取得 member_no
        → 走既有的 vote_checkin(member_no) 路徑
```

**選舉相關的三張表完全不必碰。** 統編查到多筆時（團體會員最多 3 位代表共用一個統編）列出來讓他選，取錯人會讓真正到場的代表報不了到。

## 七、報到狀態目前散在三個地方

實作前要先決定哪一個是「這個人到底有沒有到」的唯一事實來源：

| 位置 | 代表什麼 | 誰在寫 |
|---|---|---|
| `tada_v_members.is_checked_in` | 選舉報到領票 | `rpc/vote_checkin`（報到機） |
| `tada_guests.checked_in` | 貴賓報到 | 目前只有後臺手動 |
| `tada_rsvp.checked_in` | 電子會員證被掃描 | `supabase/tada_checkin.sql` 加的欄位 |

三者語意不同（領票／到場／掃證），但現場人員問的是同一句「他到了沒」。

本次擴充**只寫前兩個**（會員走 `vote_checkin`、貴賓走新的 `guest_checkin`），`tada_rsvp.checked_in` 維持現狀不動。若之後要統一，建議做一個 `tada_v_checkin_all` 的彙總 view，而不是搬移資料 —— 三個欄位各有既有的寫入者，搬動風險高於收益。

## 八、要執行的 SQL

`supabase/tada_checkin_types.sql`（可重複執行）：

- `tada_checkin_types` —— 身分別設定，報到機的按鈕由這張表驅動；已種入「我是會員」「我是貴賓」
- `tada_guests.checked_in_at` —— 補一個報到時間欄位
- `tada_checkin_pending` —— 現場補登，含 `resolution`（補進名冊／併到既有／作廢）
- `rpc/guest_checkin(p_guest_id)` —— 貴賓報到，悲觀鎖防重複，**不核發選票**
- `rpc/checkin_progress(p_election)` —— 會員與貴賓的已報到數與總數一次回傳
- `rpc/checkin_manual(p_type, p_name, p_raw, p_org)` —— 補登，只寫 pending 表

`tada_checkin_pending` **不開 anon 讀取** —— 補登名單只有後臺看得到，寫入一律經過 `checkin_manual`。

## 九、與 roasted-fish-queueing 的關係

這套需求最初寫在 `roasted-fish-queueing`（叼貓候位系統）的分支上，但**那份設計的前提是錯的** —— 它假設要從零建一套名冊與報到資料表、並串接外部協會系統。

實際上協會系統就是本專案：Supabase、`tada_members`、`tada_guests`、可運作的報到機都已經存在，**工作量比原設計小得多**，而且不該把資料分散到兩個系統。

原分支的設計文件僅供參考流程與畫面構想，資料模型部分作廢。
